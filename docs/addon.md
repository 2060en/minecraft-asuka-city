# 附加內容開發

記錄專門為這個世界製作的附加內容（資源包＋行為包）：目標、做法、基岩版的技術限制與構想清單。

> 技術面的說明以 2026 年 10 月的基岩版（1.26.60 前後）為準，標記「待實測」的要在遊戲裡確認。Claude 提出的做法在作者同意前都是「待決定」，選項整理在最後的[待決定事項](#待決定事項)。

---

## 1. 目標與方向

### 目標（已定）

- 做一套專門給這個世界用的附加內容，資源包與行為包一體
- 想到什麼、需要什麼才加，會一直持續添加
- 不能違反[可拔除原則](technical.md#2-建造原則原汁原味)：拔掉之後不影響體驗，放了錦上添花
- 作者最初的構想：原本是「某類」東西的原版方塊，用魔法棒點擊才變成自製的樣子；拔掉附加內容後，它還是原本那類的原版方塊

### 作者的顧慮：拔掉後的外觀

第一版提案是「載體方塊」（見[曾考慮的做法](#曾考慮的做法載體方塊)）：例如玻璃地板門其實是上蠟的銅地板門，拔掉附加內容就顯示成銅地板門。作者指出這樣拔掉後外觀差太多，一樣違反原則。

原版本來就顯示不出新外觀，任何新外觀拔掉後都一定會變樣，差別只在「變成什麼」。載體方塊的問題是退路被載體綁死，不是作者在原版時會選的東西。

### 雙版本（已定）

作者提出的做法：

- 主要在**附加內容版**上建造
- 發布時，用轉換程式找出整張地圖的自製方塊，換成指定的原版方塊，輸出**原味版**
- 可拔除原則的意義跟著改變：主世界可以依賴附加內容，但隨時都要能轉出完整的原味版

就像程式的原始碼與編譯產物：附加內容版是唯一的原始版本，原味版是轉換出來的，不另外維護。

### 原版替代的準則（已定）

**每一個自製的東西，都要有好的原版替代；想不到好的原版替代，就先不做**，放進[暫緩](#42-暫緩)。

例如更立體的鐵軌、換成燈飾的烽火台與螢光石，都是因為還想不到好的原版替代而暫緩。原版替代也可以是「不顯示」，例如咖啡杯。

## 2. 做法

### 三種東西分開處理

| 類型 | 例子 | 原味版怎麼來 |
| --- | --- | --- |
| 自製方塊（行為包＋資源包） | 單色門、單色地板門、外帶咖啡杯 | 轉換程式換成對照的原版方塊 |
| 原版東西換材質（只用資源包） | 物品框架、發光物品框架、畫、NPC 皮膚、界伏蚌盒、漏斗、終界燭的粒子 | 不用轉換：拿掉資源包就是原版的樣子 |
| 原版功能 | Image map 做的地圖畫 | 兩個版本完全一樣 |

### 對照表

每一種自製方塊都要登記一個原版對照（包含方向、開關等狀態怎麼對應），寫成一個檔案放在 repo 裡：`addon/mapping.json`（第一版，2026-11-02）。轉換程式、這份文件都以這張表為準。

**規則：沒有登記對照的自製方塊，不能放進世界。** 對照在做出方塊的當下就決定，不要等到發布時才回頭想。

對照也可以是空氣，也就是原味版裡直接不顯示。適合小型擺飾，例如咖啡杯（已定）。

### 轉換程式（自己寫，暫不開工）

作者決定自己寫，放在這個 repo，但先不開工（2026-11-03）。下面是 Claude 的做法提案，開工時再確認。

- 在遊戲外處理存檔的**副本**，主世界不動
- 遊戲內的腳本只能讀寫已載入的區塊，8000 × 8000 格的地圖不適合在遊戲裡逐格掃描
- 基岩版的存檔把每 16 × 16 × 16 格的區段存成「調色盤＋索引」：區段裡用到哪幾種方塊列在調色盤，每一格只記編號。所以只要把調色盤裡的自製方塊換成對照的原版方塊就好，不用逐格處理，整張地圖也很快；用結構方塊、`/fill` 放的方塊一樣抓得到
- 遇到對照表沒有的自製方塊就停下來報錯，避免漏掉的方塊在原味版變成未知方塊
- 對照到有方塊實體的原版方塊時，要一併補上方塊實體的資料（待實測）
- **不要等到發布才寫**：附加內容哪天壞掉時，它是退路。建議和[備份](technical.md#6-存檔與備份)一起跑，每次確認轉出來的原味版打得開、沒有未知方塊

### 魔法棒（不做，2026-11-02）

自製方塊可以直接從物品欄拿出來放，作者決定不做魔法棒。原本的用途是把世界裡已經蓋好的原版門、地板門原地換成單色門、單色地板門。

### 風險

| 風險 | 對策 |
| --- | --- |
| 遊戲自動更新後附加內容壞掉，主世界的自製方塊變成未知方塊 | 已知的行為是資料會保留、附加內容修好後恢復（待實測，要最先測）；大更新前先備份；只用穩定版的功能，不開實驗性功能 |
| 自製物品或實體放進世界（例如放進箱子、物品框架） | 拔掉附加內容後會消失。原本的原則「世界裡只放自製方塊，不放自製物品與實體」作者決定拿掉（2026-11-03）：自製實體消失沒關係，作者考慮過了。原味版裡自製實體直接不存在，轉換程式要把它們刪掉（遊戲會不會自己清掉，待實測） |
| 結構方塊存起來的結構裡有自製方塊 | 結構只當快取用（見[技術文檔第 5 節](technical.md#5-結構方塊)），原味版不需要 |

## 3. 基岩版的技術限制

| 項目 | 說明 |
| --- | --- |
| 資源包只能換原版方塊的材質，不能換形狀 | 原版方塊的形狀寫死在遊戲裡：門還是門的形狀，漏斗還是漏斗的形狀 |
| 原版方塊換材質是整種一起換 | 同一種方塊沒辦法這格換、那格不換，也不能依方向、開關等狀態換不同的圖 |
| 自製方塊能做的事 | 自己的形狀（模型）、半透明、動畫、發光、方向與開關等狀態。門與地板門的開關、兩格高的門、點擊增加個數、對紅石訊號的反應，都要另外寫腳本（穩定版的 Script API 沒有「這格有沒有通電」的查詢，改成看周圍方塊的紅石強度，作者實測沒問題，2026-11-03） |
| 自製方塊拔掉後 | 變成未知方塊，自製物品與實體會消失 |
| 腳本 | 只用穩定版的 Script API，不用需要開啟實驗性功能（Beta API）的部分，見[技術文檔第 4 節](technical.md#實驗性功能事件)的教訓 |

查原版的材質檔名、方塊狀態時，以 Mojang 官方公開的原版資源包與行為包為準：<https://github.com/Mojang/bedrock-samples>

#### 傳送履帶（不做，2026-11-03）

做到第三版時，作者發現在鐵軌上面放黑色坐墊就能當履帶，決定不做自製的履帶：履帶機身方塊、跟著鐵軌換形狀的腳本、煤炭方塊上的履帶外觀實體都從 Asuka tech 移除（v0.4.0）。做過的外觀改成一個只換材質的材質包「Rail to Belt」，見 [5.2](#52-rail-to-belt)。做法的討論與草稿留在 git 紀錄與 `addon/drafts/conveyor/`。

一共 8 種尺寸、38 幅。另外 `kz.png` 裡還有 4 幅 2 × 2 的 Earth、Wind、Fire、Water（地、風、火、水），是遊戲檔案裡有、但正常遊玩拿不到的畫：放畫時遊戲不會挑到它們，基岩版也沒有能指定圖案的指令，所以作者玩了 10 年都沒看過。Mojang 沒有正式說明它們的由來。要讓它們出現，只能用外部工具直接改存檔裡那幅畫的圖案名稱；同樣的方法也能把任何一幅畫指定成想要的圖案，不用靠隨機（寫入的是原版資料，符合可拔除原則；作者決定不用，2026-11-02）。一格大小的畫有 8 幅，其中 2 幅已經是筆電。

- **用法（已定）**：常用、到處重複出現的廣告用畫；特定地點的看板才用 Image map 的地圖畫，因為地圖畫比較耗效能，而且每一格各自受光線影響，相鄰的格子明暗會斷層
- 最大只有 4 × 4。更大的屋頂看板要用好幾幅拼，或用 Image map 的地圖畫
- **數量有上限**：畫的種類寫死在遊戲裡，基岩版目前查不到能用附加內容新增畫的方法（Java 版 1.21 起可以），所以廣告最多就是上表的 38 幅，加上只能靠改存檔放的地、風、火、水 4 幅。改存檔的「指定」也只是從這些現有的圖案裡挑，不是新增
- **超過的部分用 Image map 的地圖畫**：數量不限，每格 128 × 128 像素（畫只有 16 × 16），放在一般框裡像海報，放在發光框裡會亮，像燈箱或電子看板；拔掉附加內容後完全不變，只有框的樣子回到原版
- **拔掉之後**：換了材質的畫會顯示原版的圖案；改存檔指定成地、風、火、水的畫，會顯示那四幅原版的元素畫
- **廣告的材質畫成 32x**（已定，2026-11-01）：1 格 32 像素，2 × 1 也放得下一行漢字。`kz.png` 跟著變成 512 × 512，筆電的部分放大兩倍；1.21 加入的畫只換有廣告的那幾幅。後來改成 64x，遊戲可以正確顯示（作者實測，2026-11-03）。做法見[廣告清單的材質](ads.md#材質已定)
- 同一種尺寸裡，放畫時是隨機挑一幅，沒辦法指定（新版能不能指定，待確認）；同一種尺寸的廣告最好可以互換，或接受要重放幾次

## 5. 開發方式

作者同意照這一節做（2026-11-03）。

- **名稱與識別碼**（已定，2026-11-02）：附加內容叫 **Asuka tech**（作者取的）；自製方塊的識別碼前綴是 `asukatech`（Claude 取的），例如 `asukatech:door_white`。放進正式世界後就不能改
- **作者**（已定，2026-11-03）：之後開發的所有附加內容，作者都寫「asuka tech」（`manifest.json` 的 `metadata.authors`）
- **介紹用英文**（已定，2026-11-03）：之後開發的所有附加內容，介紹（`manifest.json` 或語言檔的 description）都用英文
- **原始檔放在這個 repo**：資源包、行為包、對照表、轉換程式都放在 repo，每加一個東西就 commit，修改紀錄都留著
- **安裝方式：雙擊 `.mcaddon` 匯入**（已定，2026-11-03）。不用開發用資料夾的目錄連結：附加內容已經套用到主世界，開發用資料夾裡的包和主世界是同一個包，改到一半的東西會直接影響主世界。主世界只在作者決定匯入新版時才會變
- **版本號由 `build.py` 自動加**（已定，2026-11-03）：遊戲只有在版本號比較大時才會蓋掉舊版。`build.py` 把組好的內容（manifest 以外的檔案，圖片看像素）算成雜湊，和 `addon/pack/release.json` 記的比較；內容有變就把最後一位加一，寫回兩個 `manifest.json` 與 `release.json`，跟著改動一起 commit；沒變就維持原本的版本號，同一個 commit 在誰的電腦上組都一樣。要跳大一點的版本（例如 0.5.0），手動改 `resource/manifest.json` 的版本號，`build.py` 會照用、不再加一
- 之後如果要大量反覆微調外觀，可以另做一個不同 UUID 的開發版，只在世界副本上啟用，搭配開發用資料夾（目前不做）
- **只掛在這個世界上**：不全域啟用，其他世界不受影響
- **材質解析度**：作者近期沒有用其他材質包，自製材質照原版的 16x 畫（1 格 16 像素）。例外是廣告的畫，用 64x（已定，2026-11-02）
- **先在副本上測試**：新東西先在世界副本上試，穩定後才套用到正式世界
- **封存**：穩定的版本打包成 `.mcaddon` 存一份，換電腦或備份時用
- **工具**：材質用像素繪圖軟體畫；自製方塊的形狀用 Blockbench 做

### 外觀設計流程（暫定）

外觀直接在和 Claude 的對話裡討論：

1. Claude 把每一個東西的草稿放在 `addon/drafts/<名稱>/`：`build.py` 產生基岩版的模型檔（`.geo.json`）與材質（`.png`），`preview.json` 設定要看的角度
2. 用 `tools/preview/` 的預覽工具（three.js 加無頭瀏覽器）算出預覽圖 `preview.png`，傳給作者看
3. 作者提意見，Claude 修改後重新算圖；作者也可以用 Blockbench 打開同一份 `.geo.json` 自己轉著看或修改
4. 定稿後再搬進正式的資源包與行為包

Claude 沒辦法操作 Blockbench 的畫面。預覽圖的明暗仿照遊戲裡方塊各面的亮度，實際效果以遊戲裡為準。

**草稿的座標（2026-11-03）**：草稿的 `.geo.json` 與預覽工具用的是 Blockbench「畫面上」的樣子；基岩版的模型檔存法不同（X 左右相反、X 與 Y 軸的旋轉正負相反、上下兩面的貼圖轉 180 度），Blockbench 匯入、匯出時會自動轉換。`addon/pack/build.py` 匯出到附加內容時照同樣的規則轉換，所以遊戲裡和預覽圖一樣。要用 Blockbench 打開，請開 `addon/build/Asuka tech RP/models/` 裡匯出的模型；直接開草稿的檔案會左右相反

3. **紅石**：穩定版的 Script API 沒有「這格有沒有通電」的查詢，現在是看自己與周圍方塊的紅石強度，可能有漏判（例如被中繼器充能的方塊）
4. **咖啡杯**：拿杯子點杯子時，是加杯數還是在旁邊放一個新杯子
5. **1024 × 1024 的 `kz.png` 與 64x 的單幅畫**能不能正確顯示；畫的背面是不是每一格一個蘋果標誌
6. **終界燭**：粒子是否真的不顯示；同一個粒子（`minecraft:endrod`）如果還有其他東西在用，也會一起消失
7. **置物櫃**：每個方向的門是不是都正著顯示；空的發光框架在暗處會不會亮
8. **對照表**：原版地板門 `direction` 0～3 對應哪個方向、`door_hinge_bit` 的方向：和 `addon/mapping.json` 寫的一致

## 6. 研究：盾牌與旗幟的自訂圖案

作者問：有沒有像 Image map 一樣的外部工具，可以設定盾牌的圖案？了解以下方法後，作者決定**先不做**（2026-10-31）。

**沒有像 Image map 那樣能放任意圖片的工具。** 地圖畫在存檔裡存的是每一格像素的顏色，所以外部工具可以寫進任何圖片；盾牌和旗幟存的只是「底色＋幾層（圖案形狀、顏色）」，形狀只能從原版既有的圖案裡挑，沒有存像素的地方。

可行的方法：

| 方法 | 做法 | 限制 | 原味版 |
| --- | --- | --- | --- |
| 原版旗幟圖案 | 用織布機把圖案疊在旗幟上，再和盾牌合成。網路上有旗幟設計工具，可以先排好要疊哪幾層 | 只能用原版的形狀，織布機最多疊 6 層 | 一樣 |
| 外部工具改物品資料 | 用 NBT 編輯工具直接寫進超過 6 層的圖案 | 形狀一樣只能用原版的；超過 6 層能不能正常顯示，待實測 | 一樣 |
| 資源包換掉旗幟圖案的形狀 | 把平常用不到的特殊圖案（例如 Mojang 標誌、地球、苦力怕、頭顱、花朵、豬布林鼻子）換成自己的形狀，例如國徽、公司標誌。每一層是一個顏色，多色的標誌拆成幾層疊起來。旗幟與盾牌都適用 | 每一層只有一個顏色，最多 6 層；換掉後所有用到那個圖案的旗幟都會變。如果圖案的上色方式是相乘，畫成彩色、用白色染料套上去就能一層顯示全彩，待實測 | 顯示原本的圖案（例如地球），要判斷算不算好的原版替代 |
| 資源包換掉盾牌本身的材質 | 直接畫一張全彩的盾牌，例如警察的鎮暴盾牌 | 所有沒套旗幟的盾牌都會變成同一個樣子 | 原版的木頭盾牌 |
| 地圖畫 | 如果只是想把標誌掛在牆上，用 Image map 做地圖畫放進物品框架 | 不是盾牌的形狀 | 一樣 |

## 曾考慮的做法：載體方塊

每一種自製外觀配一種平常用不到的原版方塊當「載體」，資源包只換載體的材質，魔法棒把點到的方塊換成載體。例如上蠟的銅地板門在原版和未上蠟的長得一樣，改掉也不損失原版外觀，可以當玻璃地板門的載體。

- 優點：主世界不依賴附加內容，拔掉後不會出現未知方塊，也不需要轉換程式
- 缺點：拔掉後顯示成載體（例如銅門），外觀差太多；只能換材質，做不出新形狀；原版方塊換材質是整種一起換
- 結果：作者認為拔掉後的外觀違反原則，不採用
